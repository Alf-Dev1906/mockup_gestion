MODELOS DISPONIBLES Y SU ROL EN ESTE PROYECTO
----------------------------------------------

  NOTA CRITICA: Deepseek v3.2, MiniMax M2.5, MiniMax M2.1 y GLM-5
  NO soportan imagenes ni adjuntos visuales. En sesiones de trabajo
  real donde se comparten capturas de pantalla con errores, estos
  modelos no pueden participar. Por esa razon han sido REMOVIDOS
  del plan de ejecucion y sus tareas reasignadas.

  MODELOS ACTIVOS EN ESTE PROYECTO:

  Claude Sonnet 4.5  (1.3x) - EL QUE ESTAMOS USANDO AHORA
    Soporta imagenes: SI
    Rol: Director tecnico del proyecto. Coordinacion general,
    integracion entre bloques, revision de consistencia y
    todas las decisiones arquitectonicas de alto nivel.
    Recibe capturas de errores, consola del navegador y
    logs del servidor para diagnosticar problemas.
    Cuando usarlo: sesiones principales, integracion entre
    bloques, errores que requieren ver imagen de pantalla,
    cualquier cambio en archivos criticos existentes.

  Claude Sonnet 4    (1.3x)
    Soporta imagenes: SI
    Rol: Alternativa identica a Sonnet 4.5. Mismo nivel de
    capacidad para codigo, arquitectura y analisis visual.
    Usar si Sonnet 4.5 no esta disponible.

  Claude Haiku 4.5   (0.4x)
    Soporta imagenes: SI
    Rol: Caballo de trabajo del proyecto. Cubre TODO lo que
    antes se asignaba a Deepseek, MiniMax y GLM-5 pero con
    la ventaja de soportar imagenes.
    Casos de uso:
      - Logica de backend: esquemas BD, algoritmos, validaciones
      - Logica Vue 3 reactiva: composables, Pinia stores, eventos
      - Cualquier tarea de codigo que no requiera conocer el
        sistema existente completo
      - Cuando el usuario comparte una imagen y la tarea es
        moderadamente compleja pero no critica para la integracion

  Qwen3 Coder Next   (0.05x)
    Soporta imagenes: NO
    Rol: Generador de codigo repetitivo con esquema ya definido.
    Migraciones PHP, componentes Tailwind estaticos, tablas HTML,
    formularios simples. Solo se usa cuando la tarea es 100%
    transcripcion de un esquema o patron ya escrito.
    IMPORTANTE: No pasarle imagenes. Solo texto e instrucciones.
    Cuando NO usarlo: si hay ambiguedad en los requisitos,
    si el codigo debe integrarse con archivos existentes,
    si el usuario puede necesitar compartir una captura.

PASO 2.1 - Disenar el contrato JSON para cada tipo de pregunta
  Modelo: Claude Haiku 4.5 (0.4x)
  Por que: Disenar estructuras JSON anidadas que soporten 5 tipos
  distintos con campos condicionales requiere abstraccion de datos
  precisa. Haiku 4.5 cubre esta tarea con solvencia y ademas puede
  recibir capturas si el usuario necesita mostrar un ejemplo visual
  de como se veria una pregunta en pantalla.

  TIPO 1 - Seleccion Multiple (una o varias correctas)
    contenido: {
      "opciones": [
        {"id": "a", "texto": "...", "es_correcta": true},
        {"id": "b", "texto": "...", "es_correcta": false}
      ],
      "permite_multiple": false
    }
    respuesta estudiante: {"seleccionadas": ["a"]}

  TIPO 2 - Verdadero/Falso con justificacion obligatoria
    contenido: {
      "afirmacion": "El agua hierve a 100 grados C al nivel del mar",
      "respuesta_correcta": true,
      "justificacion_requerida": true,
      "puntos_justificacion": 2.0
    }
    respuesta estudiante: {
      "valor": true,
      "justificacion": "Porque a esa presion..."
    }

  TIPO 3 - Relacion de columnas (emparejamiento)
    contenido: {
      "columna_a": [
        {"id": "1", "texto": "Termino A"}
      ],
      "columna_b": [
        {"id": "x", "texto": "Definicion X"}
      ],
      "pares_correctos": [{"a": "1", "b": "x"}],
      "mezclar_columna_b": true
    }
    respuesta estudiante: {"pares": [{"a": "1", "b": "x"}]}

  TIPO 5 - Multimedia con entrega de archivo

      "descripcion": "Analiza el siguiente diagrama...",

==================================================================
   BLOQUE 3 - SISTEMA ANTI-COPIA EN VIVO (Proctoring Lite)
==================================================================

DESCRIPCION
  Mientras el estudiante realiza un examen, el sistema detecta
  comportamientos sospechosos: cambio de pestana, perdida de foco,
  salir de pantalla completa. Cada evento registra una advertencia.
  Al superar el maximo permitido, el examen se envia automaticamente.

PASO 3.1 - Logica de deteccion de eventos (JavaScript/Vue 3)
  Modelo: Claude Haiku 4.5 (0.4x)
  Por que: Capturar visibilitychange y blur correctamente, sin
  falsos positivos (ej: el alumno cierra un modal propio de la
  app), requiere logica cuidadosa con guards.

  Composable a crear: frontend/src/composables/useProctoring.js

  Eventos a detectar:
    document.addEventListener('visibilitychange', handler)
    window.addEventListener('blur', handler)
    document.addEventListener('fullscreenchange', handler)

  Guards para evitar falsos positivos:
    - Ignorar blur si el foco fue a un <input> del mismo documento
    - Ignorar visibilitychange durante los primeros 3 segundos
    - Debounce de 500ms en blur para evitar dobles disparos

  Flujo por evento detectado:
    1. Incrementar advertencias_count en Pinia store
    2. Llamar POST /estudiante/quizzes/{id}/incidencia con tipo
    3. Mostrar modal de advertencia con contador (X de Y)
    4. Si advertencias_count >= advertencias_max:
         -> Llamar POST /estudiante/quizzes/{id}/enviar
         -> Navegar a pantalla de "examen enviado automaticamente"

PASO 3.2 - Timer regresivo sincronizado con backend
  Modelo: Claude Haiku 4.5 (0.4x)

  Store Pinia: frontend/src/stores/exam.js
    state: {
      attemptId, quizId, tiempoRestante,
      advertencias, advertenciasMax,
      estado (en_progreso | enviado | bloqueado)
    }
    action syncTimer(): cada 30 segundos enviar PATCH al backend
      con tiempo_restante_seg actual. Asi si el alumno recarga,
      el tiempo no se reinicia.
    action tick(): setInterval cada 1 segundo, decrementa
      tiempoRestante. Si llega a 0: auto-submit.

PASO 3.3 - Backend: endpoint de incidencias y auto-submit
  Modelo: Claude Sonnet 4.5 (nosotros)
  
  POST /estudiante/quizzes/{id}/incidencia
    - Valida que el attempt pertenece al estudiante autenticado
    - Registra en exam_incidents
    - Incrementa advertencias_count en quiz_attempts
    - Retorna advertencias_count y advertencias_max
    - Si advertencias_count >= max: llama auto-submit interno

  POST /estudiante/quizzes/{id}/enviar
    - Marca attempt.estado = 'enviado' o 'calificado'
    - Llama a QuizGraderService::grade()
    - Guarda nota_obtenida
    - Retorna resultado

  Modelo: Claude Haiku 4.5 (0.4x)
  Por que: La seguridad del sistema depende de que el codigo sea
  correcto, este dentro de la ventana de tiempo y que la BD
  rechace duplicados. Haiku 4.5 maneja esta logica critica de
  backend con precision y soporta imagenes si el usuario necesita
  mostrar capturas del flujo de asistencia.

  Endpoints a crear en AttendanceController.php:

  [profesor]
    POST /profesor/asistencia/abrir-sesion
      - Crea attendance_sessions con codigo aleatorio de 6 digitos
      - El codigo expira en N minutos (configurable)
      - Retorna el codigo para que el profesor lo muestre en clase

    GET /profesor/asistencia/sesion-activa/{horario_id}
      - Retorna la sesion abierta actualmente para ese horario
      - Incluye el codigo, tiempo restante y lista de presentes

    POST /profesor/asistencia/cerrar-sesion/{sesion_id}
      - Cierra la sesion (abierta=false)
      - Marca como ausentes a todos los inscritos sin registro

    GET /profesor/asistencia/historial/{horario_id}
      - Lista todas las sesiones con porcentajes de asistencia

    PUT /profesor/asistencia/{attendance_id}/justificar
      - UNICA accion de modificacion permitida: cambiar
        estatus a 'justificado'. No puede cambiar nada mas.

  [estudiante]
    POST /estudiante/asistencia/marcar
      - Payload: {horario_id, codigo}
      - Verifica que codigo == attendance_sessions.codigo_dinamico
      - Verifica que NOW() <= codigo_expira_at
      - Verifica que abierta == true
      - Intenta INSERT en attendances
      - Si falla por UNIQUE: retornar "ya registrada"
      - Si tiene exito: incrementar total_presentes

  Regla de inmutabilidad en el modelo Attendance.php:
    protected static function booted() {
      static::updating(fn() => throw new ImmutableRecordException());
      static::deleting(fn() => throw new ImmutableRecordException());
    }
    Solo el campo 'observacion' y 'estatus' (para justificacion)
    pueden actualizarse, via un metodo justificar() controlado.

DIRECTRICES GENERALES DEL PROYECTO
------------------------------------

  1. NUNCA romper los modelos existentes
     Estudiante, Inscripcion, Horario, Profesor, Materia
     son la base. El Aula Virtual se conecta SIEMPRE
     a traves de horario_id, no directamente a materia_id.

  2. Respuestar API consistentes
     Todos los endpoints nuevos usan el mismo formato:
       { "success": true, "data": {...} }
     Igual que los controladores existentes.

  3. Middleware de roles
     Las rutas del profesor usan: middleware('role:profesor')
     Las rutas del estudiante usan: middleware('role:estudiante')
     Igual que en routes/api.php actual.

  4. La pantalla de examen es un caso especial
     /estudiante/examenes/:id debe tener layout limpio (sin
     sidebar ni header) para no dar puntos de escape al
     estudiante durante el examen.

  5. Columnas JSON con cast en Laravel
     Todos los modelos con columna JSON deben tener:
       protected  = ['contenido' => 'array'];
     Asi se puede acceder como ->contenido['opciones']

  6. Transacciones en operaciones criticas
     Envio de examen, registro de asistencia y entrega de
     tarea deben usar DB::transaction() para garantizar
     consistencia en caso de error a mitad del proceso.

  7. Indices compuestos en tablas de alta lectura
     attendances: INDEX(horario_id, session_date)
     notifications: INDEX(user_id, leida)
     quiz_attempts: INDEX(quiz_id, estudiante_id)
     Estos indices son criticos para que las vistas
     en vivo no hagan table-scans completos.

  8. Storage de archivos
     Usar storage/app/public/ con enlaces simbolicos.
     Organizar por tipo:
       storage/quizzes/{quiz_id}/           (archivos multimedia)
       storage/submissions/{assignment_id}/ (entregas)
       storage/assignments/{id}/            (guias del profesor)

CUANDO ESCALAR A SONNET 4.5
-----------------------------

  Usar Sonnet 4.5 (nosotros) cuando:
    - El codigo nuevo debe integrarse con codigo existente
    - Hay un error que no tiene causa obvia
    - Dos bloques deben comunicarse y hay conflicto
    - Se necesita tomar una decision de diseno
    - Se va a tocar AdminLayout.vue, router/index.js o api.php
    - Se detecta que un modelo menor produjo algo incorrecto

  No usar Sonnet 4.5 cuando:
    - La tarea es escribir migraciones siguiendo un esquema dado
    - La tarea es maquetar una tabla HTML con Tailwind
    - La tarea es un formulario simple de Vue 3
    - La logica ya esta definida y solo hay que transcribirla

  Usar Haiku 4.5 (nivel 2) cuando:
    - La tarea requiere disenar logica nueva (BD, algoritmo, store)
    - El usuario puede compartir una imagen durante la sesion
    - El codigo es nuevo y no toca archivos criticos existentes
    - Es la primera vez que se trabaja ese modulo o funcionalidad

  Usar Qwen3 Coder Next (nivel 3) solo cuando:
    - La especificacion esta escrita 100% en texto en este documento
    - Es transcripcion pura: 'toma este esquema y escribe el .php'
    - No hay posibilidad de que el usuario comparta una imagen
    - Si hay cualquier duda: subir a Haiku 4.5
